# 13 Deploy experience: plans, step checklist, redaction

Users see **what will change before it changes**, watch a deployment as a **checklist that ticks live**, and are told in plain language what failed and what to do. **No secret value is ever shown anywhere.** Backend M17e, UI M18c. Builds on 08 (apply, health, rollback) and 10 (events).

## Deploy plan (dry run) — M17e

| ID | Rule |
|---|---|
| PLN-001 | `POST /namespaces/{ns}/stacks/{stack}/plans {revision, action: apply\|teardown}` computes a **deploy plan** without writing anything to the cluster: render (K8S-024) → policy (`policy.Evaluate`) → ownership/Argo precheck (K8S-041..043) → server-side apply with `dryRun=All` per object (field manager `control-8`, `Force: false`) → diff of the dry-run result against the live object (fresh GET, normalised: no `managedFields`, `status`, `resourceVersion`, `generation`, `uid`, timestamps) → prune candidates (labelled objects not in the revision) → grant/EA and approval requirements. Teardown plans list every object to delete (PVCs marked "kept"). |
| PLN-002 | Plan content per object: `action` `create` \| `update` \| `unchanged` \| `prune` \| `delete` \| `kept`, and a **before → after** summary: images (repo:tag and digest from → to; "to" digest resolved best-effort from the registry with a 5 s timeout, else "resolved at pull"), replicas, resource requests/limits, env var **names** added/changed/removed (values per RED rules), container ports, probes (changed: yes/no + which), ConfigMap keys added/changed/removed, non-Control-8 labels/annotations changed, `service.spec.ports`/`type`. Plus a redacted unified diff per object. |
| PLN-003 | Plan-level: `policy_result`, `conflicts` (SSA field conflicts with manager names, ownership/Argo refusals), `requires_grant` (+ whether the caller currently holds one), `requires_approval` (protected DB), **impact** (per workload: pod template changed ⇒ "restarts N pods" using `spec.replicas`, else "no restart"; prune/delete counts), `warnings` (e.g. literal sensitive env values, POL-R16). |
| PLN-004 | Plans are **stored** (`deploy_plan`, expires after 15 min) with a `hash` over: rendered revision, every live object's `resourceVersion` (or "absent"), the effective policy version and the stack's `desired_revision`. |
| PLN-005 | **Deploy this plan**: `POST .../deployments {revision, plan, ...}` binds the deployment to the plan. At request time the server compares live `resourceVersion`s (from the managed informer cache) with the plan: any difference → **409 `plan_stale`** (re-run dry run). At worker start the dry run is repeated; if its hash differs, the "Dry-run validation" step fails with `plan_stale` and nothing is applied. Strict refusal, not a warning: what was reviewed is what is applied. |
| PLN-006 | A deployment requested **without** `plan` (API compatibility, digest-poll updates) computes an implicit plan at worker start, stores it and links it, so every deployment has a plan to show. |
| PLN-007 | Dry run is read-only: allowed for product members with role ≥ `operator` **without** an EA grant, also on prod-tier stacks (deploy still needs the grant). Audited (`deploy_plan.create`), rate-limited to 10 plans per user per stack per minute (429), timeout 30 s, never takes the per-stack mutex, never writes (asserted in tests by unchanged `resourceVersion`s). |

## Deployment steps (checklist) — M17e

| ID | Rule |
|---|---|
| STP-001 | `deployment_step` rows (02): `deployment_id`, `seq`, `key`, `parent_key` (sub-steps), `label`, `status` `pending` \| `running` \| `succeeded` \| `failed` \| `skipped`, `started_at`, `finished_at`, `detail` (redacted JSON: before/after, counts), `error_code`, `message` (plain language), `hint` (what to do next), `docs_url` (`docs/ops/troubleshooting.md#<code>`). |
| STP-002 | All top-level steps are created `pending` when the deployment is created, so the whole checklist is visible from the start; sub-steps are added as they become known. When a step fails, every later top-level step becomes `skipped` except the rollback steps (STP-004). Exactly one step is the **first failure** (`first_failure: true`). |
| STP-003 | **Apply catalogue** (order): `accepted` Request accepted → `access` Access check (role; EA grant id, "not required", or "bypassed: break-glass") → `approval` Approval (4-eyes; `skipped` when not required) → `policy` Policy check → `ownership` Ownership check → `dry_run` Dry-run validation (plan match, PLN-005) → `apply` Apply (sub-step per object `apply:<Kind>/<name>`: created/updated/unchanged + before→after) → `image_pull` Image pull (sub-step per changed container image: "Pulling repo:tag" → "Pulled" (digest) or `image_pull_failed` with the sanitised `ErrImagePull`/`ImagePullBackOff` reason) → `rollout` Rollout (sub-step per workload: updated/ready/available counts; reasons from pod conditions/statuses: `Unschedulable`, `CrashLoopBackOff`, `CreateContainerConfigError`, `OOMKilled`, `ProgressDeadlineExceeded`) → `health` Health check (08 criteria) → `prune` Prune old objects (sub-step per object) → `done` Done. |
| STP-004 | On a failed apply/rollout of a `managed_rollout` stack with a predecessor, steps `rollback` Rollback (restoring revision N, with sub-steps like apply/rollout) and `rollback_result` Rolled back / Rollback failed are appended. |
| STP-005 | Other catalogues: **teardown** `accepted`, `access`, `approval`, `delete` (per object; PVCs "kept"), `done`; **adopt/release** (M21) `accepted`, `access`, `policy`, `ownership`, `dry_run` (generation unchanged), `label` (per object), `done`. Steps are a projection of what the executor does; the existing `rollout` JSON stays and is derived from the same data. |
| STP-006 | Image pull and pod reasons come from the managed informers (pods, K8S-060) plus a namespace-scoped **Event** informer (field selector `involvedObject.kind=Pod`) that runs only while a deployment of a stack in that namespace is running, filtered to the stack's pods. Without RBAC for `events` the step still works from container statuses (no "Pulling" sub-step). Messages pass through RED-020. |
| STP-007 | Error catalogue (code → message → hint): `image_pull_failed` "Kubernetes could not pull `repo:tag`: <reason>" → "Check the tag exists and the cluster can reach the registry (imagePullSecrets)"; `unschedulable` "No node can run the pod: <reason>" → "Lower resource requests or add capacity"; `crash_loop` "The container starts and exits repeatedly (exit code N)" → "Check application logs; the previous revision is being restored" (managed) or "…redeploy the previous revision" (as-is); `config_error` (missing ConfigMap/Secret reference); `progress_deadline`; `rollout_timeout`; `ownership_conflict` (managers listed); `policy_violation`; `grant_expired`; `plan_stale`; `forbidden_by_rbac`; `invalid_manifests`; `target_unreachable`. `docs/ops/troubleshooting.md` has one anchor per code. |
| STP-008 | Steps are persisted on every status change and at most once per second per running step for counter updates; they survive restarts (a deployment recovered after a restart marks its running step `failed` with `interrupted`). |
| STP-009 | `GET /deployments/{id}` returns `steps` (tree, ordered) and `plan` (id + summary). Steps publish `deployment.step` events (10) coalesced to ≤ 2/s per step; replay via the normal buffer; the page rebuilds from `GET` after reload or `reset`. |

## Redaction (central, fail-closed) — M17e

`internal/redact` is the single place that decides what may be shown. Every outward path goes through it: API responses (plans, diffs, steps, revisions, deployment output, errors), SSE payloads (last-mile check in the publisher), audit `details`, webhook payloads, and logs (slog `ReplaceAttr`).

| ID | Rule |
|---|---|
| RED-001 | **Secrets**: `Secret` objects are never fetched for display, rendered or diffed (POL-R14 already forbids them in manifests); if one is encountered it is shown only as "Secret `<name>` (hidden)". |
| RED-002 | `env[].valueFrom.secretKeyRef` / `envFrom.secretRef` / secret volumes: shown as "from secret `<secret>` key `<key>` (value hidden)" — the secret **name and key** are references the user already wrote in the manifest and are shown by default; `C8_REDACT_SECRET_REFS=hidden` replaces them with "from a secret (hidden)". Values are never read. |
| RED-003 | `imagePullSecrets` and registry credentials: never shown; plans show only "image pull secret configured (hidden)". |
| RED-004 | **Env var values** are shown only when the name is not sensitive **and** the value does not look like a credential; otherwise `•••• (hidden)`. Sensitive name = any `_`/`-`/`.`-separated token (case-insensitive) in: `PASSWORD`, `PASSWD`, `PASS`, `PWD`, `SECRET`, `TOKEN`, `KEY`, `APIKEY`, `CREDENTIAL(S)`, `CRED(S)`, `PRIVATE`, `CERT`, `PEM`, `DSN`, `AUTH`, `SESSION`, `COOKIE`, `SALT`, `SIGNATURE`, `SIG`, or the whole name matches `*_URL`/`*_URI` **with** credential-like value, `DATABASE_URL`, `CONNECTION_STRING`. |
| RED-005 | Credential-like value = URL with userinfo (`scheme://user:pass@`), JWT (`eyJ…​.…​.…`), PEM block (`-----BEGIN`), `Bearer `/`Basic ` prefixes, known token shapes (`AKIA[0-9A-Z]{16}`, `gh[pousr]_…`, `xox[abpr]-…`, `glpat-…`, `sk-…`, `c8_…`), or a high-entropy string (≥ 20 chars of base64/hex alphabet with Shannon entropy ≥ 3.5 bits/char). |
| RED-006 | **ConfigMap** data/binaryData values follow RED-004/005 per key; `binaryData` is always hidden; `C8_REDACT_CONFIGMAP_VALUES=keys-only` shows keys only. |
| RED-007 | **Fail-closed**: a value that is not valid UTF-8, longer than 4 KiB, multi-line, or that the redactor cannot classify is hidden; a parse error masks the whole field; unknown fields in Kubernetes messages are scanned with RED-005 patterns token by token. |
| RED-008 | **Diffs never leak through change markers**: a hidden field appears as `~ env.DB_PASSWORD: changed (hidden)` or `= … unchanged (hidden)`, never with before/after, and the text diff is produced from already-redacted documents (comparison of raw values happens inside the redactor only). |
| RED-009 | Revisions: `GET` returns redacted `manifests_input`/`rendered`. To keep editing possible, hidden values appear as the token `__C8_HIDDEN__`; `POST .../revisions {base_revision: N, manifests}` replaces each `__C8_HIDDEN__` with the value at the same path in revision N (422 `hidden_value_unresolved` if none). Copying an app to another environment uses server-side `copy_from: {stack, revision}` so values never round-trip through the browser (amends UI-043). |
| RED-010 | Extra patterns are additive only: `C8_REDACT_EXTRA_NAME_PATTERNS`, `C8_REDACT_EXTRA_VALUE_PATTERNS` (regex lists); built-ins cannot be disabled. |
| RED-011 | Policy POL-R16 (warning, not violation): a literal env value whose name or value is sensitive → "use a secretKeyRef". |
| RED-020 | Kubernetes event/condition/status messages and API error texts are sanitised: userinfo in URLs → `scheme://***@host`, RED-005 matches → `••••`, truncated to 500 chars. |
| RED-030 | Tests: table tests per rule (names, values, URLs, JWT, PEM, entropy edge cases); a Go fuzz test asserting that for any (name, value) classified sensitive, the value never appears in the serialised plan/diff/step/event/audit output; and the M16 redaction test extended into a **canary test** on kind: a stack with a `secretKeyRef` env, a literal `DB_PASSWORD=<canary>` env and a ConfigMap `API_TOKEN: <canary>` is dry-run, deployed, failed and rolled back; every API response, SSE stream, audit row, webhook body, log line and the DB `output`/`detail` columns are grepped for the canaries → none. |

## Audit and events

| Item | Rule |
|---|---|
| Audit | `deploy_plan.create` (who, stack, revision, plan hash, counts); deployment audit unchanged plus `details.plan`. Steps are not audited individually (they are observations of one audited action). |
| Events | `deployment.step` (`DeploymentStep` + `deployment`, `namespace`, `product`), same audience as `deployment.updated`. `deployment.updated` carries `steps_summary` (current step, first failure). |
